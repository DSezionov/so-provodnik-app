# Provodnik — планировщик заданий Stay Out

Техническое задание на MVP. Документ лежит в корне репозитория и является главным источником требований для разработки (в т.ч. через Claude Code).

---

## 1. Зачем это приложение

В Stay Out можно взять до 50 заданий (разовые, многоразовые, заказы с доски), но закрепить на экране — только 3. Игроку с 6+ активными заданиями сложно спланировать вылазку: к каким NPC идти, в каком порядке, что взять с собой, ничего не забыв.

**Provodnik — это расширенная «доска закрепов».** Игрок добавляет задания, которые у него сейчас висят, а приложение:

1. подтягивает из вики, куда идти, с кем говорить и что нужно принести;
2. строит маршрут — последовательность остановок по локациям и NPC;
3. собирает общий чек-лист предметов;
4. даёт отмечать прогресс прямо во время игры.

Каталог заданий — вспомогательный инструмент (поиск, чтобы добавить задание в журнал), а не самоцель.

## 2. Жёсткие ограничения

| Ограничение | Следствие |
|---|---|
| Хостинг — **GitHub Pages** | Только статика. Никакого бэкенда, БД на сервере, авторизации. |
| Бесплатный план GitHub | Репозиторий **публичный**. |
| Адрес вида `username.github.io/<repo>/` | `base` в Vite, scope и `start_url` service worker'а настраиваются под подпуть с первого коммита. |
| Данные с [so-wiki.ru](https://so-wiki.ru) | Сбор — **только на этапе сборки** (GitHub Actions), не из браузера пользователя. |
| Лицензия вики — CC BY 4.0 | Ссылка на первоисточник у каждого задания + общая атрибуция в футере/«О приложении». |
| Этикет по отношению к вики | Перед парсингом прочитать `robots.txt` и соблюдать его. Не трогать запрещённые пути (`/w/` целиком, включая `api.php`; `Special:`/`Служебная:`; `/wiki/edit/` и др. — см. §3). Честный User-Agent с названием проекта и ссылкой на репозиторий, пауза между запросами — `Crawl-delay` из robots.txt (сейчас 5 с; это приоритетнее общего «≤ 1 запрос/сек»), локальный кэш ответов, инкрементальное обновление по дате правки. |
| Данные неполные и неструктурированные | **Ничего не угадываем.** Неизвестное помечаем явно (см. §4.3). |

## 3. Источник данных: что известно о so-wiki.ru

Проверено в Фазе 0 (2026-10-18), подробности — `data/report.md` и `scraper/README.md`.

### 3.1. Доступ и ограничения

- Движок: **MediaWiki 1.43 + Semantic MediaWiki**.
- **`robots.txt` запрещает для всех ботов `/w/`** — то есть `/w/api.php` (MediaWiki API и SMW `action=ask` / `browsebysubject`) и `/w/index.php`. Также запрещены `/wiki/Special:`, `/wiki/Служебная:`, `/wiki/edit/`, `/wiki/history/`, `/wiki/purge/`, `/wiki/info/`, параметры `diff=`, `oldid=`, `action=history|edit|purge`, `limit=250|500`. `Crawl-delay: 5`. `ClaudeBot` заблокирован полностью (нас как UA не касается, но упоминается в письме админу).
- **Пока админ не ответит — источник только отрендеренный HTML `/wiki/<Страница>` и страницы-списки.** `?action=raw` формально не запрещён, но не используется без явного разрешения.
- Разрешён `sitemap.xml` (→ `sitemap-so-wiki.ru-NS_0-0.xml.gz`): 4679 страниц основного пространства с `lastmod` — основа инкрементального обновления.
- Сетевая доступность: с IP владельца (UA) сайт недоступен без VPN; облачный фетчер Anthropic получает `ECONNREFUSED`. Доступ из GitHub Actions проверяется в начале Фазы 1 (см. §4.1).

### 3.2. Страницы-списки (встроенные результаты SMW)

Страницы-списки содержат в `mw.config` JSON результата SMW-запроса (формат `datatables`) — свойства доступны без API:

| Страница | SMW-запрос | Строк | Свойства |
|---|---|---|---|
| `Задания` | `[[Категория:Задания]]` | 1760 | Периодичность, Опыт, Деньги |
| `Разовое` | `[[Тип задания::Разовое]]` | 552 | Опыт, Деньги |
| `Многоразовое` | `[[Тип задания::Многоразовое]]` | 931 | Периодичность, Опыт, Деньги |
| `Подработка` | `[[Тип задания::Подработка]]` | 51 | Периодичность, Опыт, Деньги |
| `Персонажи` | `[[Категория:Персонажи]]` | 517 | Локация, Профессия, Начинает задания, Торгует, Меняет |

Справочники без SMW: `Локации` (18 локаций), `Предметы` + `Артефакты` (≈884 предмета) — списки ссылок. Страницы мобов-справочника нет (`Мутанты` — 404).

В MVP входит **1534** задания (Разовое + Многоразовое + Подработка); 226 — вне объёма. Из многоразовых 134 — вариации `(Групп) <задание> (<локация/база>)` ≈ 40 базовых заданий.

### 3.3. Страница задания

Собирается шаблоном `Шаблон:Задание`; разметка стабильна (CSS-классы), в `RLCONF` есть `wgRevisionId`, `wgCategories`.

- **Инфобокс** (`.quest-base-info`, строки `.infobox-row`) — структурированные поля:
  - Тип задания, Периодичность («23 часа»);
  - **Начало:** NPC [Локация]; **Конец:** NPC [Локация] **или «автозавершение»**;
  - **Особые условия** (необязательно): пороги репутации, время суток («с 07:00 до 00:00»), выбор в диалоге, членство в группировке;
  - **Предыдущее задание** — список со статусом в скобках. Встречаются: `[выполнено]`, `[в наличии]`, `[в наличии или выполнено]`, `[выполнено или провалено]`, `[в наличии, выполнено или провалено]`, `[нет в наличии и не выполнено]`. Между списками иногда **явно** стоят разделители `и` / `или`;
  - **Следующее задание** — список (у «раздатчиков» это варианты, из которых выдаётся одно случайное);
  - Глава / Список подглав (сюжетные цепочки).
- **Описание** — свободный текст; у многоэтапных — пронумерованные **этапы журнала** («1. Найти шапку…») — формулировки, которые игрок видит в игре. Скрытые задания помечены плашкой «Скрытое задание».
- **Процесс выполнения** — свободный текст, но с опорами:
  - многоэтапные — абзацы «1. … 2. …», число совпадает с этапами журнала;
  - требуемые предметы — шаблон `Требуется`: иконка + ссылка + «– N шт.» или «– от X до Y шт.» (у подработок — всегда диапазон);
  - квадраты вида `I3-1`, `AI7-3`, `AA2` после слова «квадрат…»;
  - ссылки на локации/NPC; точки на карте (`Шаблон:Точка_на_карте`: слой + lat/lon);
  - плашки «Совет» / «Примечание» (типовые плашки «отмена задания» и «правила подработок» — шаблонный текст, не задания).
- **Награда** (`div.reward.*`): деньги, опыт, репутация по группировкам (иногда с условием), очки торговли, очки группировки, предметы × N. У подработок награда указана **за единицу** предмета/убийства.

**Главный риск** сместился: инфобокс, предметы и награды структурированы; эвристикой остаются разбиение на шаги, локация/NPC шага, тип шага, цели убийства. В выборке 50 заданий: локация названа явно у 43% шагов, с учётом NPC и «сдачи у конечного NPC» — у 88%; квадрат — у 40%.

## 4. Данные

### 4.1. Пайплайн

```
scraper/ (Python 3.12 в CI; код совместим с 3.9)
  fetch  → robots.txt → sitemap (lastmod) → страницы-списки и справочники → страницы заданий;
           сырой HTML в scraper/cache/ (в .gitignore), условные запросы (ETag / If-Modified-Since)
  parse  → нормализация в модели §4.2
  report → data/report.md: сколько заданий, % распознанных полей, список проблемных страниц
  build  → public/data/*.json (минифицированные, с полем version = дата сборки)
```

**Источник (решение по итогам Фазы 0):** только отрендеренный HTML `/wiki/…` (BeautifulSoup) + встроенные результаты SMW на страницах-списках (§3.2). `api.php`, `Special:` и `action=raw` не используются, пока админ вики явно не разрешит. `mwparserfromhell` не нужен, пока нет доступа к wikitext.

**Этикет загрузчика:** каждый URL проверяется по robots.txt до отправки; пауза между запросами = `max(1 с, Crawl-delay)` (сейчас 5 с); User-Agent `ProvodnikBot/<версия> (+https://github.com/DSezionov/so-provodnik-app)`; перекачиваются только страницы с изменившимся `lastmod` в sitemap. Первый полный сбор ≈ 1545 запросов × 5 с ≈ 2 ч 10 мин.

**Запуск:** весь сборщик — **одна локальная команда** (fetch → parse → report → build), без зависимости от CI.

**CI (`data.yml`)** — в начале Фазы 1 проверяется доступ из GitHub Actions (только запрос `robots.txt`):
- если доступ есть — по расписанию (раз в неделю) и вручную (`workflow_dispatch`): сборщик с персистентным кэшем (`actions/cache`) → если данные изменились, коммит JSON → деплой Pages;
- если доступа нет — сборщик запускает владелец локально, JSON коммитится вручную; CI только собирает фронтенд и деплоит.

**Полный сбор всех 1534 заданий откладывается до ответа админа.** До этого фронтенд работает на данных выборки из 50 заданий (`scraper/sample_titles.json`).

### 4.2. Модель данных (JSON)

```ts
type Confidence = "wiki" | "parsed" | "unknown";
// wiki    — взято из структурированного поля вики
// parsed  — извлечено эвристикой из свободного текста
// unknown — не удалось определить; UI показывает «проверь на вики»

interface Quest {
  id: string;               // стабильный slug из заголовка страницы
  title: string;            // как на вики (RU)
  url: string;              // ссылка на первоисточник
  type: "once" | "repeatable" | "board" | "other";
  periodHours?: number;
  hidden: boolean;          // «Скрытое задание»: нет в игровом журнале; в данных есть (нужно для связей)
  variant?: VariantRef;     // вариация одного задания (напр. «(Групп) Бинт антисептический (Вез)»)
  start?: NpcRef;           // NPC + локация
  end?: QuestEnd;           // NPC сдачи или автозавершение
  conditions: string[];     // «Особые условия» как на вики (репутация, время суток, диалог…)
  prev: QuestLink[];        // предварительные условия
  prevLogic: "and" | "or" | "unknown";
  next: string[];           // id
  journalStages: string[];  // этапы журнала из описания, как их видит игрок (может быть пусто)
  steps: Step[];            // этапы в порядке выполнения
  rewards: Reward[];
  description?: string;     // короткий текст для превью, без пронумерованных этапов журнала
  rawProcess: string;       // исходный текст «Процесса выполнения» (всегда показываем)
  tip?: string;
  notes: string[];          // плашки «Примечание» (кроме шаблонного текста)
  revision: number;         // wgRevisionId страницы
  updatedAt: string;        // lastmod из sitemap
}

interface NpcRef { npcId: string; locationId?: string; confidence: Confidence }
type QuestEnd =
  | ({ kind: "npc" } & NpcRef)
  | { kind: "auto"; confidence: "wiki" };   // «автозавершение»: остановки «сдать» нет

interface VariantRef {
  groupId: string;          // общий id группы вариаций (из заголовка без суффикса)
  label: string;            // отличие вариации: «Вез», «ЧЛ», «База: Заброшенный рудник»…
  confidence: Confidence;   // "parsed" — группа выведена из шаблона заголовка
}

type QuestState = "taken" | "done" | "failed" | "none";  // none = не взято и не выполнено
interface QuestLink {
  questId: string;
  states: QuestState[] | "unknown";  // какие состояния предыдущего задания подходят
  statusRaw?: string;                // текст статуса как на вики: «в наличии или выполнено»
}

interface Qty { min: number; max?: number }  // точное число: min === max; «от 2 шт.»: только min

interface Step {
  order: number;
  kind: "talk" | "deliver" | "collect" | "kill" | "goto" | "other";
  text: string;             // человекочитаемая формулировка
  npcId?: string;
  places: StepPlace[];      // 0 — локация не определена; 1 — обычный шаг; >1 — любой из вариантов
  items: ItemReq[];         // только из шаблона «Требуется»
  kills: KillReq[];
  confidence: Confidence;
}

interface StepPlace {
  locationId: string;
  squares: string[];        // «I3-1»; может быть несколько или ни одного
  confidence: Confidence;   // "parsed" — из текста шага или по локации NPC; "wiki" — из инфобокса
}

interface ItemReq { itemId: string; qty?: Qty; confidence: Confidence }
interface KillReq { mobId?: string; name: string; qty?: Qty; confidence: Confidence }  // mobId — slug страницы моба, если есть ссылка

interface Reward {
  kind: "money" | "xp" | "rep" | "trade" | "group" | "item";
  value: number | string;
  target?: string;          // группировка / предмет
  note?: string;            // условие: «при наличии у … больше 3000 очков репутации»
  perUnit?: boolean;        // награда за единицу (у подработок): итог = value × выданное количество
}

// Справочники: npcs.json, locations.json, items.json — { id, name, url, locationId? }
```

**Правила заполнения:**

- `prevLogic`: `and` / `or` — только когда вики явно ставит разделители `и` / `или` между списками (все разделители одинаковые). Смешанные разделители («A или B и C» — приоритет вики не определяет) и несколько условий без разделителей → `unknown`. Одно условие → `and` (при одном условии «И» и «ИЛИ» совпадают — это не вывод, а тождество).
- `QuestLink.states`: статус разбирается на слова «в наличии» → `taken`, «выполнено» → `done`, «провалено» → `failed`; «нет в наличии и не выполнено» → `["none"]`; незнакомая формулировка → `"unknown"` + `statusRaw`.
- `variant`: группа по шаблону заголовка `(Групп) <задание> (<суффикс>)`. Префиксы группировок вроде `(Бар у ЛВЗ) Специи` — **не** вариации (разные предметы), это разные задания.
- `places` при отсутствии локации в тексте шага: локация названного в шаге NPC (инфобокс или справочник `Персонажи`) → `parsed`; последний шаг → локация `end` (`wiki`); иначе пусто («Локация не определена»).
- `journalStages`: пронумерованные абзацы описания. Если их число совпадает с числом шагов — этап N соответствует шагу N.

Минимальный «скелет» шага, если текст не разобрать: задание из 2 шагов — «взять у `start`» и «сдать `end`», с `confidence: "wiki"`, плюс `rawProcess` целиком; при `end.kind = "auto"` — только «взять у `start`». Так маршрут строится всегда, даже при плохом парсинге.

### 4.3. Правила честности данных

- Каждое поле, полученное эвристикой, имеет `confidence: "parsed"`; UI помечает его.
- Логику «И/ИЛИ» для предварительных условий не выводим, если вики её явно не указывает → `prevLogic: "unknown"`.
- Количество предмета не найдено → `qty` отсутствует, в чек-листе «? шт.». Диапазон «от X до Y» не сворачиваем в одно число.
- Требуемые предметы — **только из шаблона `Требуется`**. Ссылки на предметы в свободном тексте (награды, выдаваемое снаряжение, упоминания) в требования не попадают; квестовые предметы без ссылки («передайте образцы») не выдумываются.
- Текст «Процесса выполнения» показывается всегда, под разобранными шагами.

### 4.4. Объём данных в MVP

Входят: **Разовое, Многоразовое, Подработка** (заказы с доски).
Не входят: Праздничное, PvP, Соревнование (структура иная, для планировщика вылазок мало пользы).

## 5. Функциональность MVP

### 5.1. Журнал (главный экран)

- Список активных заданий игрока, **лимит 50** (как в игре), счётчик `N/50`.
- Добавление:
  - поиск по названию / NPC / локации (fuzzy, без учёта регистра и `ё/е`, с учётом кавычек в названиях вроде `"Беленькая" для Свекольного`); можно добавить несколько подряд, не закрывая поиск;
  - **вставка списка текстом** (по строке на задание) → сопоставление → экран подтверждения: распознано / несколько кандидатов (выбрать) / не найдено.
  - скрытые задания (`hidden`) в поиске по умолчанию не показываются; переключатель «показать скрытые», в результатах — пометка «скрытое»;
  - вариации одной группы (`variant.groupId`) в поиске — одна строка, вариация выбирается при добавлении.
- Для задания с вариациями — выбор вариации. Для многоэтапного — выбор текущего этапа («я уже на шаге 3»); подписи этапов — из `journalStages` (формулировки из игрового журнала), если их нет — текст шага.
- Для предметов с диапазоном (`qty.max > qty.min` или нет `max`) — можно указать фактическое количество, которое выдала игра.
- **Порядок заданий задаётся вручную** (drag & drop, на мобильном — удобные ручки/кнопки вверх-вниз). Этот порядок = приоритет для маршрута.
- Действия: «сдано» (убрать из журнала, предложить следующее задание из `next`, если его выдаёт тот же NPC), удалить.

### 5.2. Маршрут (автоматический, из порядка заданий)

Вход: упорядоченный список заданий, у каждого — оставшиеся шаги (с текущего этапа). Шаги внутри задания строго последовательны; между заданиями — независимы.

Алгоритм (жадное слияние, детерминированный):

```
указатель[q] = первый невыполненный шаг каждого задания q
текущая_локация = локация первого доступного шага задания с наивысшим приоритетом
пока есть невыполненные шаги:
  доступные = { указатель[q] для всех q }
  здесь = доступные, у которых локация == текущая_локация
  если здесь не пусто:
      сгруппировать «здесь» по NPC (порядок групп — по приоритету самого раннего задания в группе)
      добавить остановку(и) в маршрут, сдвинуть указатели этих заданий
      (повторять, пока в этой локации появляются новые доступные шаги — цепочки внутри локации)
  иначе:
      текущая_локация = локация доступного шага задания с наивысшим приоритетом
шаги без известной локации → отдельный блок «Локация не определена» в конце, с пометкой
```

Локация шага для алгоритма:

- один `place` — его локация;
- несколько `places` (любой из вариантов) — вариант в `текущая_локация`, если он есть, иначе первый; остановка показывает альтернативы («или: Везувий E2-2, Тунгуска C2-4, …»);
- `places` пуст — блок «Локация не определена».

Особые случаи:

- **Убийства** (`kind: "kill"` / непустые `kills`) — отдельная остановка «Охота: <моб> — N шт.» в локации шага, не сливается с остановками у NPC.
- **Автозавершение** (`end.kind = "auto"`) — остановки «сдать» нет; задание завершается последним шагом.
- **Сдача у конечного NPC**: если последний разобранный шаг не у `end`-NPC, в маршрут добавляется шаг «сдать `end`» (`wiki`).
- **Особые условия** (`conditions`) показываются на остановке значком-предупреждением (напр. время суток «с 07:00 до 00:00»); маршрут их не учитывает.

Результат: список **остановок**, сгруппированных по **локациям** → внутри по **NPC/точке** («Химик · Везувий · I3-1: сдать X (задание A), сдать Y (задание B)»). Повторные визиты к одному NPC в одной локации сливаются, если это не нарушает порядок шагов внутри задания.

Карта и расстояния в MVP не учитываются (координат-графа нет). Пользователь может вручную поменять местами блоки локаций — тогда маршрут пересчитывается с этим порядком локаций как ограничением. Кнопка «сбросить к авто».

### 5.3. Чек-лист «что взять»

- Предметы из всех оставшихся шагов, **суммированные по `itemId`**: «Аккумулятор — 6 шт. (A: 3, B: 3)».
- Диапазоны суммируются по границам: «Пустая бутылочка — 5–20 шт. (A: 5–20)»; «от 2 шт.» без верхней границы → сумма «от N шт.». Если игрок указал фактическое количество (§5.1) — берётся оно.
- Предметы с `qty` неизвестно — «? шт.» (и сумма по предмету помечается «неполная»); с `confidence: parsed` — значок «авто, проверь».
- **Отдельный блок «Убить»** из `kills` оставшихся шагов, суммированный по `mobId` (или `name`, если ссылки нет), с теми же правилами количеств. В «что взять» убийства не смешиваются.
- Задания, у которых предметы не распознаны вообще, — отдельный список «проверь требования на вики» со ссылками.
- Галочки «есть с собой». Отметки на остановках маршрута («сделано»). Всё сохраняется.

### 5.4. Карточка задания

Тип, периодичность, NPC начала/конца с локациями, этапы (разобранные) + исходный текст процесса, совет, награды, предыдущие/следующие задания со статусом, ссылка «открыть на so-wiki.ru». Кнопка «в журнал».

### 5.5. Связи заданий (минимум)

- Показ предыдущих и следующих заданий.
- Подсказка в журнале: «после сдачи A у того же NPC станет доступно B».
- Если пользователь добавил задание, а его `prev` (с `prevLogic: "and"`) не отмечены в журнале как сданные — мягкое предупреждение. При `unknown` — только информирование, без блокировки.

### 5.6. Сохранение, экспорт, ссылка

- Всё состояние пользователя (журнал, порядок, этапы, галочки, ручной порядок локаций) — в **IndexedDB** (Dexie). Версия схемы + миграции.
- Экспорт/импорт журнала в JSON-файл.
- **Ссылка-план:** `#/plan?d=<lz-string(compressed JSON: id заданий, этапы, порядок)>`. Если URL длиннее ~2000 символов — предложить экспорт файлом.
- Синхронизации между устройствами в MVP нет.

### 5.7. PWA и офлайн

- `vite-plugin-pwa`, манифест, иконки, установка на главный экран (iOS/Android).
- Precache оболочки приложения и `public/data/*.json`.
- При новой версии данных — ненавязчивый баннер «Данные вики обновлены».
- Всё работает без сети после первого открытия.

### 5.8. Языки интерфейса

- **RU / UK / EN**, переключатель в настройках, по умолчанию — язык браузера, fallback RU.
- Переводятся **только строки интерфейса**. Названия заданий, NPC, предметов и тексты из вики остаются на русском (как в источнике) — это явно сказано в «О приложении».
- Все строки — через ключи i18n, без хардкода текста в компонентах.

### 5.9. Адаптивность

Mobile-first: основной сценарий — телефон рядом с ПК во время игры. Тёмная тема по умолчанию (+ светлая). Крупные зоны нажатия для галочек.

## 8. Критерии готовности MVP

- [ ] Добавить 6 заданий за < 1 минуты (поиском или вставкой списка).
- [ ] Маршрут строится для любого набора, включая задания с плохо распознанными шагами (через «скелет»).
- [ ] Чек-лист суммирует одинаковые предметы и честно показывает неизвестное.
- [ ] Отметки переживают перезагрузку и работу без сети.
- [ ] Ссылка-план открывается на другом устройстве и воспроизводит журнал.
- [ ] Интерфейс переключается между RU/UK/EN без перезагрузки.
- [ ] Каждое задание ссылается на свою страницу so-wiki.ru; атрибуция CC BY есть.
- [ ] Lighthouse PWA: устанавливается, работает офлайн.

## 9. Не входит в MVP

Нативные приложения (позже — через Capacitor), синхронизация между устройствами, аккаунты, учёт карты/расстояний и переходов между локациями, PvP/праздничные/соревнования, перевод игрового контента, правки данных пользователями.

**Отложено по итогам Фазы 0** (украшения каталога, не влияют на маршрут, чек-лист и честность данных; парсер их уже извлекает):

- точки на карте шагов (`Шаблон:Точка_на_карте`: слой + lat/lon) — пригодятся для будущей карты;
- сюжетные главы и подглавы (`Глава`, `Список подглав`) — показ цепочки в карточке;
- группировка заданий по префиксу (`(Бар у ЛВЗ)`, `(Красно)` …) как фильтр каталога;
- разбор «Особых условий» в структуру (пороги репутации, время суток) — в MVP только текст;
- признак «раздатчика» (следующее задание выдаётся случайно из списка) — в MVP `next` плоский.
